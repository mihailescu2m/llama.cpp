# DeepSeek-V4-Flash-0731

> Research log. Measured on **M1 Max, 64 GB, ~400 GB/s**, streaming experts from SSD.

A 284B mixture-of-experts model on a machine with 64 GB of RAM. The routed experts — the
overwhelming majority of the weights — never become resident. They are streamed from SSD on demand
into a bounded cache, so the usable checkpoint size is set by **disk throughput, not by RAM**.

Decode at depth is dominated by the KV read rather than by weight traffic, which is why streaming
the experts costs so little once the context is deep. That is the premise of this work, and the
reason the model runs well especially at larger contexts — most of the optimisation effort targets
prefill and long context rather than short-prompt decode.

---

## At a glance

| | |
|---|---|
| Parameters | 284B MoE, 43 layers, 256 experts/layer, 6 active per token |
| Attention | MLA + DSA sparse attention, 64 heads, `key_length = 512` |
| Indexer | 64 heads, `key_length = 128`, `top_k = 512`, **no block compression** (`compress_ratios` are 0) |
| Expert shape | `ffn_gate/up_exps` 4096 → 2048, `ffn_down_exps` 2048 → 4096 |
| Checkpoint | `UD-iQ4-XXS`, 107.33 GiB, 4 shards (custom, see below) |
| Resident | everything except routed experts |
| Streamed | routed experts, into a 40 GiB cache |
| Speculation | n-gram (`ngram-mod`) — model-free, costs no RAM |
| KV | F16 |

```bash
llama-server -m <first shard> \
  -ngl 99 --moe-stream --moe-stream-cache 40 --moe-stream-io-threads 8 \
  -c 131072 -b 4096 -ub 4096 -np 1 -fa on \
  --spec-type ngram-mod --spec-ngram-mod-n-match 16 \
  --spec-ngram-mod-n-min 8 --spec-ngram-mod-n-max 16
```

`--moe-stream-cache 40` is the measured optimum on 64 GB — **size it to your machine, not to the
model**. `-ub 4096` is the single largest prefill parameter.

Expert streaming is enabled by the CLI flag; lookahead prefetch and pair partitioning are then on by
default. Union-8 is on by default for eligible multi-query F16 attention, with `LLAMA_DSV4_UNION=0`
selecting the per-query sparse path and `LLAMA_DSV4_UNION_MIN_NCSA` moving its crossover gate.

## The checkpoint

The default is a **custom quant**, `UD-iQ4-XXS`, built for this machine. It exists because the
off-the-shelf quants optimise for size at the expense of the one thing that matters here: **which
Metal kernels the expert tensors end up using**.

Against the previous `UD-IQ3_XXS` default it is 10.3 GiB larger, and the difference is almost
entirely in `ffn_gate_exps` and `ffn_up_exps` — where `IQ2_XS`/`IQ3_S` are replaced by `IQ3_XXS` and
`MXFP4`. That is a deliberate trade: more bytes per expert, fewer cache slots, faster kernels.

**The ranking does not follow bit width.** `IQ3_XXS` is the *worst* format per effective bit in both
regimes despite reading the fewest bytes — its kernel is occupancy-bound on this GPU, so the bytes it
saves are paid back with interest. `Q4_0`, `Q4_1` and `MXFP4` sit near the top of the 4-bit group and
`Q8_0` beats every 3-bit format outright per bit moved. This is the whole argument for a custom mix:
choose formats whose kernels suit the GPU, not formats that minimise the file.

Best-to-worst spread per effective bit is **6.8x at prefill and 5.4x at decode**, so format choice
matters in both regimes. What changes between them is the absolute winner: at `n=512` the GEMM has
arithmetic to hide the bytes behind and F16 is fastest outright, while at `n=1` the GEMV is
bandwidth-bound and `Q4_1`/`Q4_0` beat `F16` by more than 2x in wall time. A checkpoint has to serve
both, which is why the mix is not simply "the fastest format".

## What was added, and why

### Attention and prefill

| Change | Rationale |
|---|---|
| **Union-8 sparse attention** | eight queries share one deduplicated top-k list instead of eight separate gathers, with each query's exact membership preserved in an 8-bit mask packed alongside the row id |
| **Chunked union bitmap** | the threadgroup bitmap covers 65536 rows at a time and the row space is walked in chunks, so the path stays engaged at long context instead of silently falling back to dense |
| **Cap the flash-attention unroll at DK=512** | the heuristic `MIN(DK8/2, 4*NSG)` folds to 32 at DK=512 because NSG is a template parameter, spilling registers |
| **Pair-partitioned waves** | the expert GEMMs run over a partitioned pair list rather than every wave re-running over every pair with the rest masked away |

Union-8 requires at least eight queries, so single-token decode always takes the per-query sparse
path. That path is upstream's indexed sparse FA, and it is also union-8's fallback — so the two are
the live comparison, not union versus dense.

### MoE expert streaming

| Change | Rationale |
|---|---|
| **Lookahead prefetch** | issue layer *n+1*'s expert loads during layer *n*'s compute, on a separate queue so a wide prefetch cannot delay the demand read a layer is blocked on |
| **Hotness decay over 1024 tokens** | at 64 an expert accumulates ~1.5 uses between halvings, so counters cannot rank and eviction degenerates into plain LRU |
| **One work item per weight slab** | an expert's 2-3 slabs are independent reads; issuing them together is what lifts device queue depth above 1 |
| **Hash-layer prefetch** | the first layers hash the token id, gain no locality, and are a disproportionate share of steady-state misses |
| **Zero-copy expert load** | on unified memory the cache slot *is* host memory, so staging then uploading is a pure extra copy |
| **GPU-side slot resolve** | the cache-slot lookup ran on the CPU, forcing a graph split per layer; the kernel resolves it and a servicer fills the requests over a shared event |

Stall is **per layer, not per miss** — several misses inside one layer cost roughly what one does.
That single fact explains why prefetch width is cheap and why miss *count* is a poor proxy for time.

### Speculation and serving

| Change | Rationale |
|---|---|
| **n-gram speculation** (`ngram-mod`) | zero RAM, and RAM is the scarce resource here |
| **Draft context sized for the draft model** | an MoE drafter inherited the target's batch and cache budget, spending the memory speculation exists to save |
| **Slot checkpoint persistence** | a restored slot re-prefilled from scratch on an SWA model |

## Negative results

The more useful half of the log. Several of these look obviously correct on paper and cost real GPU
time to disprove.

| Idea | Result |
|---|---|
| **Depth-2 lookahead** | negative. Depth-1 is the whole win; the second layer of prediction is too wrong to pay for. |
| **i-quant LSU wide loads** | negative. The q4_0 gap is *occupancy*, not load width — see the kernel survey above. |
| **Requantising i-quants to k-quants for speed** | backwards. `Q3_K` is not faster than `IQ3_XXS` per bit; picking formats whose kernels suit the GPU is what works. |
| **MoE small-batch kernel** | wins synthetically, loses in situ — and hid an `ne11==1` broadcast bug a unit test cannot catch |
| **Scan resistance / tail-hotness** | built, measured worse, shipped off. Prefill is a small fraction of the working set; there is nothing to resist. |
| **Page-cache L2** | the page cache serves a few percent of expert reads. All `F_NOCACHE`/L2 work is dead. |
| **Removing graph splits** | removed almost all of them for no gain |
| **Block-sparse / FA block-skip** | measured dead |
| **ANE / `lm_head` offload** | declined — no path to a win worth the complexity |
| **Porting Qwen's block-level indexer top-k** | not applicable. It works because Qwen's KV is 4:1 compressed, so a block shares one score; this model ships `compress_ratios = 0` on every layer and selects individual rows. |

**Standing rule: no output-altering optimizations.** Quality is not tradeable for single-digit
percentage gains, which retires a whole class of otherwise attractive ideas — including synthesising
a block structure for the indexer that the model does not have.
